# 2026-07-16 暂停、切换车间与退出问题复盘

## 1. 问题背景

测试流程为：程序连接 MES 并开始处理任务，在提示音或中文语音尚未完成时点击“暂停播报”，随后进入系统设置切换车间筛选，最后尝试退出程序。

出现过以下现象：

- Visual Studio 在 `SoundService.PlayAsync` 中断，显示 `OperationCanceledException`。
- 调试期间 Windows 任务管理器显示应用“无响应”。
- 部分退出测试中，协调器已经停止，但进程仍未完全退出，需要任务管理器结束。
- 车间筛选配置不正确时，MES 返回“选择的车间没有对应产线”。

## 2. 本次收集到的关键证据

### 2.1 调试器中断位置

调试器停在提示音播放后的：

```csharp
cancellationToken.ThrowIfCancellationRequested();
```

此时 `IsCancellationRequested = true`。这说明系统设置重载或退出已经发出取消信号，提示音线程随后主动抛出了 `OperationCanceledException`。

该异常原本会由上层播报流程处理，但 Visual Studio 可以在异常第一次抛出时暂停整个进程。进程被调试器暂停后，Windows 窗口无法处理消息，因此任务管理器会显示“无响应”。

### 2.2 退出日志

一次典型日志顺序为：

```text
17:44:50 当前播报已取消，未确认次数
17:44:50 播报已由用户暂停
17:44:58 播报协调器已停止
```

但之后没有“程序已退出”。这证明当时卡点已经不在 MES 查询或协调器循环，而在协调器停止后的 TTS、提示音等资源释放阶段。

### 2.3 车间配置错误

另一次日志出现：

```text
选择的车间没有对应产线
```

这是独立的业务配置问题。它会触发三次重试后自动暂停，但不应导致程序无法退出。

## 3. 根因分析

### 3.1 正常取消被实现为异常控制流

提示音服务在播放前后调用 `ThrowIfCancellationRequested()`。暂停、切换设置和退出本来都是正常操作，却会通过异常结束播放任务。在非调试运行中异常可被上层捕获，但在 Visual Studio 中容易触发“用户未处理”或“已引发”中断，使进程看起来卡死。

### 3.2 提示音与 TTS 之间存在暂停竞态

旧流程为：

1. 点击暂停。
2. 调用 TTS 取消，但此时 TTS 可能尚未开始。
3. 停止正在播放的提示音。
4. 提示音任务返回后，旧代码继续启动 TTS。

因此，在提示音阶段暂停时，有机会出现“已经暂停却又开始说话”。

### 3.3 Windows TTS 取消可能同步阻塞

旧实现会在调用线程和锁内执行 `SpeechSynthesizer.SpeakAsyncCancelAll()`。Windows 语音组件处于播放、取消和释放竞争状态时，该系统调用存在长时间不返回的风险。退出流程即使已经停止协调器，也可能在释放 TTS 时停住。

### 3.4 `CancellationTokenSource.Cancel()` 同步执行回调

`.Cancel()` 会在当前线程同步调用已注册的取消回调。如果回调直接进入系统音频或 HTTP 组件，调用退出的 UI 线程也可能被拖住，外层超时逻辑甚至来不及建立。

### 3.5 资源释放缺少最终时间边界

原设计虽然等待协调器停止，但对系统 TTS、`SoundPlayer` 等底层资源释放缺少独立超时。只要其中一个系统组件不返回，进程就可能残留。

## 4. 已实施的解决方案

### 4.1 正常取消不再抛异常

- `SoundService.PlayAsync` 改为返回 `Task<bool>`。
- 完整播放返回 `true`，取消返回 `false`。
- 不再在提示音工作线程中调用 `ThrowIfCancellationRequested()`。
- `SpeechService.SpeakAsync` 同样使用布尔结果表达正常取消。
- 真正的播放故障仍然通过异常和错误日志上报。

这样可以区分：

```text
暂停/换配置/退出 → 正常取消，不报错
文件丢失/TTS 故障 → 异常，记录错误
```

### 4.2 每个播放阶段后重新检查状态

提示音结束后、TTS 结束后都会检查：

- 本阶段是否完整播放；
- 当前是否已暂停；
- 程序生命周期令牌是否已取消。

任一条件不满足就立即结束当前任务，且不向 MES 确认播报次数。

### 4.3 TTS 采用非阻塞取消

- 首先将当前朗读任务完成为 `false`，立即解除协调器等待。
- 再在线程池中调用底层 `SpeakAsyncCancelAll()`。
- 不再在 UI、协调器或退出线程中同步等待系统 TTS 取消。
- 防止迟到的 `SpeakCompleted` 事件访问已经释放的等待句柄。
- 新朗读开始前取消旧朗读，避免测试语音与正式任务重叠。

### 4.4 提示音停止改为非阻塞

`SoundPlayer.Stop()` 在线程池中执行，暂停和退出操作不会被系统音频调用直接拖住。

### 4.5 停止和释放增加分层超时

- 协调器停止：最多等待 5 秒。
- 音频及 HTTP 资源释放：最多等待 2 秒。
- 超时后记录警告并继续关闭窗口，不再无限阻塞 UI。

### 4.6 增加进程级退出看门狗

用户确认退出后启动 10 秒后台看门狗。正常退出完成时进程会自然结束；若系统音频组件永久阻塞，10 秒后调用 `Environment.Exit(0)`，保证无需任务管理器介入。

该机制只在用户明确确认退出或系统进入真正关闭流程后启动，不影响普通的“关闭到托盘”。

## 5. 数据一致性原则

暂停、切换设置或退出发生在任意播放阶段时：

- 当前提示音或 TTS 尽快停止；
- 当前次数不回写 MES；
- `broadcastedNum` 不增加；
- 任务保持待播报；
- 新配置启动后重新查询任务实际状态。

系统宁可在下一轮重新完整播放一次，也不把未完整朗读的内容标记成已播报。

## 6. 建议复测矩阵

| 场景 | 操作 | 预期结果 |
|---|---|---|
| MES 正在连接 | 暂停后换车间 | 旧连接取消，新配置重新登录和查询 |
| 提示音正在播放 | 点击暂停 | 不再进入 TTS，不回写次数 |
| TTS 正在朗读 | 点击暂停 | 朗读停止，不回写次数 |
| 已暂停 | 保存新车间 | 旧协调器有界停止，新协调器按新范围启动 |
| 提示音正在播放 | 托盘退出 | 正常快速退出，极端情况不超过约 10 秒 |
| TTS 正在朗读 | 托盘退出 | 正常快速退出，进程不残留 |
| 车间无对应产线 | 等待三次失败 | 自动暂停，但仍可正常设置和退出 |
| Visual Studio 调试 | 在播放中暂停 | 不应再停在 `ThrowIfCancellationRequested()` |

7. 任务管理器“详细信息”中进程是否仍存在，以及持续时间。

## 8. 当前结论

本次问题不是单一原因，而是“调试器遇到正常取消异常”“提示音和 TTS 之间的暂停竞态”“系统音频组件同步取消风险”和“退出缺少最终时间边界”叠加造成。现已分别在播放控制、取消语义、资源释放和进程退出四个层级增加保护，并通过 .NET Framework 4.8 Debug 重建。
